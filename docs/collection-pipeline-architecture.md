# 采集链路架构与性能分析（当前实现）

> 本文档描述**当前已实现并落地的采集方案**：从用户创建调查到平台数据入库的完整链路、
> 多平台任务的排布方式、平台内关键词的组织方式，以及当前实测的性能特征与已知瓶颈。
> 目标读者是负责分析「如何加快采集速度、保证系统可用」的专家，因此文末附候选优化方向，
> 均标注「未实现/未验证」状态，避免与已落地行为混淆。

---

## 1. 端到端流程概览

```
用户创建调查 (case)
   │  case_id、topic、时间窗口 time_range、目标平台 platforms
   ▼
定义采集方案 (Collection Definition，用户确认)
   │  goal / platforms / platform_queries（每平台关键词组）/ exclusions（排除词）/ filters
   │  激活为 Active Collection V1
   ▼
调查 Agent 决定采集
   │  Agent 调用工具 collect_social_posts（模型无权覆盖策略）
   ▼
策略决策 + 人工审批
   │  ToolPolicyEngine：restricted_process + 网络域名白名单 + 高风险需审批
   │  用户在前端审批通过后放行
   ▼
沙箱子进程执行（每组关键词一次浏览器全流程）
   │  sandbox_worker → MediaCrawlerAdapter.collect → MediaCrawler 命令
   ▼
主进程后处理
   │  时间窗口过滤 → 微博营销噪声过滤 → native_id 去重
   │  → 按天分桶覆盖采样（每天每平台 ≤150 条、每帖评论 ≤10 条）→ 排除词过滤
   ▼
入库 + 统计 Memory
   │  posts 写入社交库，覆盖统计（空窗/去重/异常词）写入调查 Memory
```

关键设计点：

- **采集是「人工审批后才放行的外部副作用」**：`collect_social_posts` 的
  `requires_approval=True`、`risk_level=high`，策略在模型决策之后、执行之前运行，模型无法覆盖。
- **采集必须通过受限子进程执行**：未装配沙箱执行器时 fail closed，绝不降级裸跑。
- **平台数据只从搜索接口抓取**：`--type search`，平台搜索 API 不保证完整历史覆盖，
  空窗天会如实报告而非补造数据。

## 2. 多平台任务排布（当前实现）

### 2.1 串行逐平台执行

一次 `collect_social_posts` 调用内，**平台之间严格串行**：同一时刻只有一个平台在跑
（`tool_factory.py` 的 crawl：`for platform in request.platforms: await _run_platform(platform, "main")`）。

这是对「5 平台并行」实测失败的修正：并行时 5 个 Chrome 同时启动瞬间把 CPU 打满，
每个平台都跑不完自己的搜索，最终全部超时，且超时后 LLM 重试又拉起新一批浏览器，
形成「5 个 Chrome 反复开关循环」。串行虽然拉长总时长，但保证每个平台都能完成一轮，
且用户能持续看到进度。

### 2.2 失败重试与队尾补采

每平台的执行策略（`_run_platform`）：

| 阶段 | 尝试次数 | 说明 |
| --- | --- | --- |
| `main`（首轮） | 最多 2 次 | 同平台连续失败 2 次才放弃本轮，转下一个平台 |
| `retry`（补采） | 1 次 | 首轮全部结束后，对首轮失败平台在队尾补采一次 |

- 首轮失败的平台进入 `deferred` 列表，**不阻塞其他平台**——成功平台照常入库，
  不让单平台故障丢弃其他平台已采集的数据。
- 补采仍失败时，失败细则（平台 / 关键词 / 阶段 / 错误摘要）进入 `platform_status`，
  随工具结果返回给 Agent 向用户报告；全部平台无内容时抛 `crawl_no_content` 明确失败。

### 2.3 并发控制预留

- 工具级：`execution_mode="sequential"`、`max_concurrency=1`（同一时刻只允许一次采集调用）。
- 平台级信号量 `_PLATFORM_CONCURRENCY=2` 已实现（防止同一平台并发过载），
  当前串行路径下不触发，保留作为未来受控并行的上限。

### 2.4 进度事件流（流式输出）

每次尝试开始 / 失败 / 完成都通过 `tool_progress` 事件实时推送（SSE → 前端时间线）：

```
platform_start   → 「正在采集 微博（第1次尝试）…」
platform_attempt_failed → 「微博 本次尝试失败：<错误摘要>」
platform_done    → 「微博 采集完成 · N 条」（或「未采到内容」）
```

用户无需等待整轮结束即可看到每个平台的状态，这是对「长时间无任何反馈」问题的修复。

### 2.5 整体超时预算

| 层级 | 上限 | 说明 |
| --- | --- | --- |
| 工具调用整体 | 3600 秒 | 容纳整轮串行（5 平台 × 重试） |
| 单条 MediaCrawler 命令 | 1800 秒 | 每组关键词一次命令的超时 |

## 3. 平台内关键词组织（当前实现）

### 3.1 关键词来源（优先级）

1. **Active Collection Definition 的 `platform_queries`**（用户确认过的定义）：
   `keywords_for()` 取请求平台与定义平台交集，每平台取定义中的关键词组；
   定义未覆盖的平台回退到 `[topic]`，不静默丢平台。
2. **LLM 检索优化**（无定义时）：`generate_platform_keywords` 按平台内容形态提示词
   生成每平台 2–3 组关键词；LLM 失败或未注入时回退 `{platform: [topic]}`。

### 3.2 执行截断：每平台最多 2 组

无论定义了多少组，**执行时每平台只跑前 2 组**（截断只影响本次执行，不修改已确认的定义）。

原因：组数直接决定串行总等待时长——实测 5 平台共 17 组导致整体超时、用户长时间拿不到数据。
2 组足以覆盖主叙事与扩展角度。

### 3.3 每组关键词 = 一次完整浏览器流程

`MediaCrawlerAdapter.collect` 对每平台的关键词组**逐组**构造一条命令并执行：

```
python main.py \
  --platform <wb|bili|tieba|zhihu|dy> \
  --lt qrcode \
  --type search \
  --keywords <该组关键词> \
  --save_data_option jsonl \
  --crawler_max_notes_count <fetch_limit_for> \
  --max_comments_count_singlenotes <min(comment_limit, 10)> \
  --get_comment true \
  --headless true \
  --max_concurrency_num 1
```

每组命令 = 一次完整浏览器会话：启动 Chrome（持久化登录态目录
`browser_data/<platform>_user_data_dir`）→ 打开搜索页 → 输入关键词 → 翻页抓取
→ 抓评论 → 写 JSONL → 关闭浏览器。

### 3.4 抓取上限

- **单平台单关键词组抓取量**：`fetch_limit_for = min(max(150 × 区间天数, 150), 600)`
  ——按时间窗口天数线性放大，但**封顶 600 条**（单次搜索接口的抓取成本上限）。
- **评论**：每帖最多 `min(comment_limit, 10)` 条，按互动量排序取前列。
- 单命令 `--max_concurrency_num 1`：组内不并行。

### 3.5 后处理（主进程）

1. **时间窗口过滤**：仅保留 `published_at` 落在 case 时间窗口内的帖子。
2. **微博营销噪声过滤**：识别账号交易 / 导流信号（如「出号 / 明盘 / 走平台 / 加微」），
   保守策略下剔除高精度命中项。
3. **native_id 去重**：多组关键词可能命中同一批帖子，按 `(platform, native_id)` 去重合并。
4. **覆盖采样（按天分桶）**：`apply_coverage` 把结果按 `(天, 平台)` 分桶，
   每天每平台经排序后最多保留 150 条；短文本（无媒体且 <10 字）丢弃、
   近重复（Jaccard ≥ 0.86）丢弃并计入统计；评论同样截断到每帖 10 条。
5. **排除词过滤**：Collection Definition 的 `exclusions` 在入库前应用。

## 4. 登录态管理

- 各平台采用 **qrcode 扫码登录**，登录态持久化在
  `vendor/MediaCrawler/browser_data/<platform>_user_data_dir`（Playwright
  persistent context），一次登录后多日复用。
- 登录失效时由运维脚本 `backend/scripts/relogin_platform.py` **逐平台**恢复：
  检查 cookie 判定键（如微博 `SSOLoginState`、B 站 `SESSDATA`、贴吧 `BDUSS`、
  知乎 `z_c0`、抖音 `LOGIN_STATUS`），未登录则打开浏览器等待扫码（240 秒超时）。
- 刻意**不**同时拉起所有平台的扫码窗——避免用户被多个弹窗淹没。

## 5. 沙箱与安全（与性能相关的约束）

- **执行类**：`restricted_process`——Windows 受限子进程（参数数组、独立临时目录、
  最小环境白名单、进程树取消）。环境只注入操作系统必需变量 + `COIFESP_*` 配置，
  子进程读不到宿主 `.env` 与业务密钥。
- **网络**：`platform_profile` 域名白名单（weibo/bilibili/tieba/zhihu/douyin 及其
  CDN 域名），默认拒绝内网/保留地址（SSRF 防护）。
- **审批**：每次采集需要用户人工批准。
- **headless**：浏览器以无头模式运行（`.env` `MEDIACRAWLER_HEADLESS=true`），
  不抢占用户前台窗口。

## 6. 当前性能特征（实测口径）

| 环节 | 量级 | 说明 |
| --- | --- | --- |
| 单组关键词浏览器流程 | 约 1–2 分钟 | 含浏览器启动、搜索、翻页、评论抓取、退出 |
| 单平台（2 组） | 约 3–5 分钟 | 2 组串行 + 启动开销 |
| 5 平台整轮（无失败） | 约 15–25 分钟 | 平台严格串行 |
| 失败放大 | 最多 ×2 尝试 + 补采 | main 阶段 2 次 + retry 1 次 |
| 用户可见反馈 | 每次尝试粒度（约 1–2 分钟一条） | 通过 tool_progress 流式推送 |

实测暴露的核心矛盾：**串行换来稳定，但总时长 = 平台数 × 组数 × 单组时长**。
5 平台 × 2 组已截断，10 组串行约 15–25 分钟；若未来恢复更多关键词组或更多平台，
时长线性恶化。

### 6.1 已知瓶颈（按影响排序）

1. **每组关键词都重启一次完整浏览器**：持久化上下文启动（含登录态校验）约 10–30 秒，
   10 组 × 启动开销不可忽视；同一平台 2 组之间完全没有复用。
2. **平台严格串行**：5 个平台排队执行，整轮时长 = 各平台之和；单核瓶颈在等待，
   而非计算（浏览器抓取大部分时间在等待网络/页面渲染）。
3. **每组都做登录态检查与完整翻页**：即使上一组刚验证过登录成功、即使搜索结果
   第一页就有足够数据，也不跳过检查或提前收手。
4. **评论抓取耗时**：每帖最多 10 条评论 × 最多 600 帖，评论抓取可能占单组时长
   的相当比例。
5. **关键词组数放大**：LLM 优化默认 2–3 组/平台，虽然执行截断到 2 组，
   但「组 = 一次完整流程」的粒度本身放大了总时长。

## 7. 候选优化方向（供专家分析，均未实现/未验证）

> 以下方向是结合当前实现与实测瓶颈提出的候选，尚未在代码中落地，需评估
> 稳定性、风控风险（平台反爬）、登录态影响后决定。

| # | 方向 | 预期收益 | 风险 / 待验证 |
| --- | --- | --- | --- |
| 1 | **同平台多关键词复用一次浏览器会话**：把同一平台的多组关键词合并为一次
      MediaCrawler 调用（上游 `--keywords` 支持逗号分隔多词），组内顺序搜索，
      只启动/关闭一次浏览器 | 消除组级启动开销，单平台 2 组可省 20–60 秒；
      平台内复用登录态校验 | 需验证上游多关键词搜索的翻页/去重行为；单命令
      超时窗口需放大 |
| 2 | **受控平台级并行**：利用已有 `_PLATFORM_CONCURRENCY=2` 信号量，把 5 平台
      从严格串行放宽为 2 路并发 | 整轮时长近似减半（15–25 分钟 → 8–13 分钟） | 
      曾因 5 路全并行 CPU 打满失败；2 路并发需实测 CPU/内存水位，且要保留
      进度流与失败隔离 |
| 3 | **登录态预热与跳过组级检查**：平台首组之前统一校验一次登录，后续组跳过 | 
      减少重复校验开销 | 需确认 MediaCrawler 是否提供「校验但不重新登录」入口 |
| 4 | **提前收手 / 动态翻页**：单组已采满 `fetch_limit_for` 或时间窗口内数据
      已覆盖时提前结束翻页 | 显著缩短单组时长（尤其是热门关键词） | 需改适配层
      或上游参数；注意搜索接口分页顺序 |
| 5 | **评论抓取分级**：先抓主帖，评论改为后台延迟抓取或按需抓取 | 主帖数据更早
      可用；单组时长下降 | 评论是分析的重要素材，需权衡完整性 |
| 6 | **增量采集 / 游标续采**：同一 case 二次采集时只抓时间窗口内新增内容 | 
      后续轮次大幅提速 | 依赖平台搜索接口的排序/分页稳定性 |
| 7 | **更宽的窗口下限调整**：`fetch_limit_for` 封顶 600 对 11 天窗口实际按
      600 抓取，可评估是否需要随窗口增长调高 | 保证长窗口覆盖率 | 与单组时长
      存在直接 trade-off |

**建议的分析主线**：优先验证 #1（同平台复用会话）与 #2（2 路受控并行）的组合——
二者分别消除「组级开销」与「平台级串行」，不互相冲突，且都建立在现有代码
（`_PLATFORM_CONCURRENCY` 信号量、`platform_status` 失败隔离、`tool_progress`
进度流）之上，改动面可控。
