# Failure Stories — 5 个真实故障与修复

> 这些不是假想题，都是这个项目真实踩过并修好的问题。每个故事按
> **现象 → 根因 → 修复 → 取舍 → 可复用的经验** 写。
> 其中 Story 3、4、5 还带"我们当时做错了什么"，因为面试里讲清失误比只讲成功更有价值。

---

## Story 1 — 同步采集把用户对话阻塞了几十分钟

**现象**
用户点"开始采集"，HTTP 请求一直挂着；采集五平台要几十分钟，期间对话不可用；
刷新页面后前端拿不到任何进度，用户不知道系统在干什么。

**根因**
采集被实现成"在请求生命周期内跑完的长任务"：请求线程既是触发器也是执行器。
后果有三层：

1. 反向代理超时后请求断开，但后端仍在跑，用户已经不知道该不该重试；
2. 没有中间状态可查，所以前端只能"转圈"；
3. 进程重启（部署、OOM）会让整轮采集凭空消失，且不留下失败记录。

**修复**
把采集从"请求的一部分"改成**一等公民的持久化任务**：

- 新增 `collection_runs` 表：`phase` / `status` / `request_json` / `progress_json` /
  `result_json` / `lease_owner` / `heartbeat_at`；
- 独立的 `CollectionRunWorker` 用租约抢占运行，心跳续约，崩溃后可被重新认领；
- 请求只负责创建 run 并立刻返回，前端轮询/订阅进度；
- 部分失败可保留 partial result，而不是全丢。

**取舍**
引入最终一致性：用户点完不会立刻看到数据。我们用"明确的任务状态 + 进度 +
可取消"来换取"请求永不阻塞"，而不是假装它还是同步的。

**可复用经验**
长任务一旦进了请求生命周期，就同时失去了可观测性、可恢复性和反压能力——
三样都补不回来。**先把任务变成记录，再谈执行。**

## Story 2 — Agent 从聊天历史里"猜"数据库事实

**现象**
用户问"这个调查现在有多少条数据？"Agent 答得很流畅，但数字是错的——它把
上一轮对话里提到的数字当成了当前事实。更糟的是，用户很难从回答里看出这一点。

**根因**
当时代理只有检索类与采集类工具，**没有直接查数据库的工具**。模型要回答"有多少条"，
唯一能用的材料就是上下文里的历史文本。这不是模型"幻觉"，而是我们的工具面太窄，
逼着模型去猜。

**修复**
新增**数据库工具包**（DB01–DB09）：`get_case_data_overview`、
`query_social_posts`、`query_social_comments`、`aggregate_social_data`、
`query_findings`、`query_review_items`、`query_reports`、`query_case_activity` 等，
全部只读、全部强制 case scope，并把它们列进 coordinator 的允许工具集。

配套地：

- 工具层的 `case_id` 由 runtime 注入，模型无法指定别的 case（越界即被丢弃）；
- 结果做白名单投影，避免把内部字段整包丢给模型；
- 评测里加了 G1（Database Grounding）类任务，专门检查"是否真的查了库"。

**取舍**
工具变多会抬高模型的选择难度。我们选择**用工具权限约束而不是用 prompt 劝阻**：
prompt 可能被绕过，权限不会。

**可复用经验**
如果模型在用"上下文里的文本"回答本该查库的问题，先反省工具面，
而不是先加一句"不要编造"的 prompt。

## Story 3 — Windows 上的 Chromium Cookie 到了 Linux 就失效

**现象**
本地（Windows）用浏览器登录采集平台一切正常；把 `browser_data` 目录拷到
Linux 服务器后，采集直接进登录页，平台侧表现为"未登录"。

**根因（两层）**

1. Chromium 的 cookie 存储在 Windows 上用 DPAPI 加密，密钥绑定当前 Windows
   用户账户。**把 profile 目录复制到 Linux 无法解密**，这不是路径问题；
2. 我们最初的设计把"登录态"当成一个**可以直接搬运的目录**，这本身就假设了
   宿主环境可迁移——一个隐含且错误的架构假设。

排查中还踩了一个自己制造的坑：诊断代码里用了类作用域的计数器（`_poll_count`），
在方法里直接引用导致 `NameError`，把"登录失败"伪装成了"代码报错"，
白白多花了一轮排查时间。

**修复**
把登录态从"可搬运的目录"改成**应用自有的可移植凭据**：

- `PlatformAuthCredential`：cookie 用 **AES-256-GCM** 加密后入库，
  AAD 绑定 `platform-auth:<id>:v1`，主密钥来自环境变量（`SecretStr`）；
- **服务端扫码登录**：在服务器上真实打开浏览器完成扫码，cookie 由应用自己导出并加密，
  不再依赖"本地登录后搬运"；
- 导出时过滤非法 cookie（RFC 6265 允许无名 cookie，百度系会出现，直接落库会报
  `cookie field 'name' is invalid`）；
- 采集时凭据由 `CredentialResolver` 解密注入，沙箱子进程内也能解析
  （这一点后来被 Story 里的采集链路问题再次验证，见下）。

**取舍**
服务端扫码意味着服务器要能跑真实浏览器；我们为此在 headless Chrome 上准备了
虚拟显示与 CDP 的能力，并把"扫码"这类必须人工介入的环节明确排除在自动评测之外。

**可复用经验**
**登录态是一种需要自己负责的可移植资产，不是宿主环境的副本。**
另外：诊断代码本身也会成为故障源——写完诊断先确认它自己不报错。

## Story 4 — 把"有界扫描"当成了完整真相集

**现象**
一个本该"仍然有效"的信号被系统自动标记为已解决（resolved）。用户看到的是
"问题消失了"，但实际上只是检测器没扫到。

**根因**
检测器为了控制成本做了**分页/有界扫描**（每次只扫一部分）。reconciliation 逻辑
把"这一轮扫描结果"当成了 truth set：

```text
扫到的 = 存在的
没扫到 = 已消失 → 执行 destructive reconcile
```

当扫描被 limit 截断时，这个推理直接失效——**没扫到只是因为没扫完**。

**修复**
让扫描结果**自带完备性**，并把完备性作为 destructive 操作的前置条件：

- 检测器返回是否被截断（`complete: true/false`）；
- reconciliation 只在 `complete == true` 时执行破坏性收敛；
- 不完整时改为"标记未确认"而不是"判定消失"，并在信号里保留该状态。

**取舍**
不完整扫描下会保留一些可能已经失效的信号（假阳性上升），而破坏性收敛会更少发生。
我们选择"宁可多留，不可错杀"，因为错误 resolved 会让用户错过仍在发酵的事件。

**可复用经验**
**任何带 limit / 采样 / 分页的检测，都必须显式返回"我扫完了吗"。**
把"没看到"当成"不存在"是数据系统里最典型的错误之一。

## Story 5 — V1 的 Debate 在重构中失去了入口

**现象**
项目早期有一版"多智能体辩论"功能，在 V2/V3 的数据模型重构后，前端入口消失、
调用链断开。功能代码还在，但**没有任何用户路径能到达它**——一个典型的
"重构过程中被遗忘的能力"。

**根因**
重构时我们把注意力放在了数据模型与主链路（采集 → 证据 → 结论 → 报告）上，
Debate 被当作"旁支"留在原地。等到要恢复时发现：

1. 它原本的操作对象（旧模型）已经不存在了；
2. 它产出的结论语义（"谁赢了辩论"）与新的关注点（"这条结论的证据是否充分"）
   已经不对齐。

**修复（重新定义而不是恢复）**
没有把旧功能硬搬回来，而是把它重新定义为 **Finding 级对抗评审**：

- 作用对象从"整个调查"收敛到"一条具体 Finding"；
- 输出从"辩论胜负"变成"支持/反对/上下文的证据对抗与评审意见"；
- **明确不自动改写 Finding 状态**：`verified` 仍只能由人工评审产生；
- 前端作为 Finding 详情页的对抗评审入口，重新接回用户路径。

**取舍**
放弃"多 Agent 辩论很酷"的展示价值，换来语义清晰和责任边界明确。
这也是 [tradeoffs.md](tradeoffs.md) 里"为什么 Debate 不自动改变 Finding"的由来。

**可复用经验**
**重构时被遗忘的功能，不要原样搬回来。**
先问它在新模型下"还应该负责什么"，再决定恢复还是重新定义。
